## 一、文章骨架

### 實作型文章（主流）

```
# 標題（含「從0開始」或痛點問句）

## 課程目標
- 3 條，用「了解」「能夠」「實際體驗」開頭

>[!Note] 基本目標（選用）
> 一句話說清楚本篇要解決什麼問題

## 為何要教這個？
[情境帶入：描述初學者真實痛點，50-150字]
[解方承諾：今天的工具怎麼解決它]

## 概念是什麼
>[!Note] 更簡單的說法
> 類比說明

[技術定義，1-2段]

## 實際操作

### 第一步：XXXXX
[截圖] + 說明句
>[!Warning] 注意事項（有需要才加）

### 第二步：XXXXX
...

## 進階挑戰（選用）
>[!Warning] 進階目標：XXXXX
[步驟邏輯 + 關鍵片段，不給完整答案]

## 挑戰 / 換你試看看
[重型：>[!Important] + :::spoiler]
[輕型：### 換你來試看看 + >[!Tip]提示]

>[!Warning]Todo List
> 1. 動詞開頭的行動
> 2. ...
```

### 工具導覽型文章（非程式）

```
# 標題

簡短介紹工具是什麼

## 基本操作
- [子頁面連結]

## 進階功能
- [子頁面連結]

# 後話
輕鬆收尾，鼓勵讀者繼續探索
```

## 二、開場公式

每篇文章幾乎不直接切入技術，固定節奏：**情境帶入 → 痛點共鳴 → 解方承諾**

| 開場方式 | 範例 |
|---------|------|
| 焦慮情境 | 「後天就要上台報告，什麼都沒開始」 |
| 問題定義 | 「想分析咖啡廳策略，需要兩個關鍵要素：好資料 + 好分析」 |
| 生活比喻 | 「原始人打獵 vs 現代人用槍——開發 AI 也一樣」 |
| 點出已知痛點 | 「你跟了兩週，有沒有發現 Linebot 根本沒有記憶？」 |

### ❌ 不像的開場 vs ✅ 像的開場

❌ 教科書式，直接定義，沒有帶入感：
```
本文將介紹如何使用 FastAPI 建立後端 API，適合有 Python 基礎的學習者。
```

✅ 先讓讀者覺得「說的就是我」，再承諾解法：
```
你有沒有想過，當你在手機上按下「登入」，資料是怎麼跑到伺服器去驗證的？
如果你現在只會寫「程式跑在自己電腦上」的 Python，那你的程式就像一把好刀，卻鎖在抽屜裡沒人能用。
今天我們要做的事，就是幫你的程式開一扇門——這就是 API 在做的事，而 FastAPI 讓這件事變超簡單。
```

## 三、類比系統

每個新技術概念必須配一個生活類比，放在 `>[!Note]` 框中，不散落在正文句子裡。

| 技術概念 | 類比 |
|---------|------|
| API Key | 圖書館借書證 |
| Secret / Properties Service | 保險箱（直接寫進程式 = 把鑰匙貼在門上） |
| NotebookLM | 圖書館管理員，只回答架上有的書 |
| Prompt Engineering | 點咖啡：「我要咖啡」vs「大杯冰美式加一包糖，燕麥奶」 |
| Firebase Collection/Document | 抽屜標籤 / 文件名稱 |
| Google Sheet ID | 試算表的獨一無二身分證 |
| Hugging Face | 現成工具箱，不用自己打鐵 |
| JSON 巢狀結構 | 一層一層撥開的洋蔥 |
| CSV 開放資料 | 政府把整桌資料擺出來，任何人都能取用 |
| `df.groupby()` | 把同標籤的人分到同一組 |
| `.getValues()` | 把試算表內容轉成 Python 看得懂的語言 |
| 工作排程器 | 鬧鐘，時間到了自動幫你按執行 |

### 遇到新概念時，造類比的方法

遇到指紋表裡沒有的概念，按這三步造：
1. 找這個技術「在做什麼動作」（儲存、查找、驗證、排隊、過濾、轉換...）
2. 對應到生活中做同樣動作的東西（倉庫、字典、借書證、叫號機、篩子、翻譯官...）
3. 加一句「限制條件」讓類比更精確

範例：
- `queue`（佇列）= 便利商店結帳排隊，先排的先結，不能插隊
- `cache`（快取）= 便條紙貼在螢幕上，常用的先寫這，不用每次去翻書
- `middleware`（中介層）= 海關，每個人進出都要先經過它檢查，才能繼續走

## 四、語氣規則

- 用「**我們**」而非「你」，建立同行感
- 口語連詞：「那我們」「其實」「沒錯」「白話來說」「先不要想那麼複雜」
- 完成一個大步驟後收尾：「這樣，我們就對 XXX 有一定認識了！」「恭喜你！」
- 系列課程整篇結尾：「Day N 收工！」
- 適時拋出反問：「奇怪，這是為什麼？」「問題來了，你要怎麼辦？」
- 偶爾插入 murmur 自我吐槽：`[name=製作人murmur : ...]`
- 引出挑戰題固定句：「是時候挑戰看看...」

### ❌ 不像的語氣 vs ✅ 像的語氣

❌ 正式、冷硬、像文件：
```
注意：直接將 API Key 寫入程式碼會有安全風險，建議使用環境變數儲存。
```

✅ 口語、有畫面、帶情緒：
```
如果直接貼上 API Key 代碼，就像把家裡的鑰匙貼在門上，誰都能輕易取得。
Secret 就像保險箱，安全地儲存敏感資訊，只有授權的程式才能存取。
```

---

❌ 結尾像論文摘要：
```
本課程結束。學員應已掌握 Gemini API 的基本使用方式。
```

✅ 結尾像助教拍肩膀：
```
這樣，我們就對 Gemini 與 Excel 的操作有一定認識了！
```

## 五、資訊框規範

| 框框 | 使用時機 |
|------|---------|
| `>[!Note]` | 解釋概念、生活類比、「更簡單的說法」 |
| `>[!Warning]` | 操作注意事項、TodoList、常見錯誤、系列前篇提醒 |
| `>[!Important]` | 重要觀念、重型挑戰題 |
| `>[!Tip]` | 小技巧、省時捷徑、輕型挑戰的提示 |
| `:::spoiler 參考答案` `:::` | 重型挑戰的正確答案，讓學生先思考再打開 |

## 六、程式碼呈現規則

- 函式 / 變數用行內反引號：`df.columns`、`getRange()`
- 重要觀念加螢光筆：`==重要內容==`（HackMD 語法）
- 每個程式碼區塊後接說明句：「以上圖為例，...」或「白話來說：...」
- 多個函式介紹時，先給「**速查表**」再補完整範例：

```markdown
### 1. 抓取試算表
- `SpreadsheetApp.openById(id)` : 透過 ID 開啟試算表
- `SpreadsheetApp.getActiveSpreadsheet()` : 取得目前關聯的試算表

### 2. 抓取 Sheet
- `spreadsheet.getSheetByName(name)` : 透過名稱取得指定 Sheet
```

- 二維結構（表格座標 / JSON 巢狀 / 二維陣列）**必須先有示意表**，再給程式碼，最後「以範例來說，...」驗證：

```markdown
| 欄位名稱 | columnIndex | 對應變數 |
|---------|------------|---------|
| 員工姓名 | 0 | nameIndex |
| 部門 | 1 | departmentIndex |
```

## 七、挑戰題設計

### 重型挑戰（程式邏輯型）
適用：有明確對錯的程式碼優化題

```markdown
>[!Important]是時候挑戰看看
> [給一個不夠好的版本，說明 2-3 個具體問題]
> 請根據上面的原則，優化他，使他能夠...

:::spoiler 參考答案
[正確版本]
:::
```

### 輕型挑戰（概念理解型）
適用：引導思考、不強求完整程式

```markdown
### 換你來試看看
[一個開放問題]

>[!Tip]提示
> 1. 想想看 XXX 應該如何...
> 2. `XXX.plot(kind='line')` = ...
```

## 八、TodoList 收尾

每個工具 / 主要段落結尾都有 TodoList，讓讀者立刻動手：

```markdown
>[!Warning]Todo List
> 1. [動詞開頭，具體可執行的行動]
> 2. 嘗試切換 XXX，觀察變化是否符合預期
> 3. 將結果貼到 / 存到 XXX
```

## 九、系列文章的接力設計

- 開頭加 `>[!Warning]在看此篇教材前` 提醒先讀前篇
- 正文主動說「跟 Day X 一樣，...」「這跟第一篇教材的 XXX 非常像！」
- 讓讀者感受到「我沒有漏掉什麼」的安心感

## 十一、【待填】當學生卡關時，我怎麼說話

> 💡 這裡填你在實際教學時，面對學生「看不懂」「跑不動」「不知道哪裡錯」的反應方式。
> 例如：你會先問哪個問題？你習慣說什麼來安撫？你會怎麼引導他自己找出問題？
>
> 參考方向：
> - 你通常第一句話說什麼？（「先看一下 error message 說什麼」vs「你的環境裝好了嗎？」）
> - 你怎麼讓學生不覺得自己很笨？
> - 你習慣的除錯引導流程是什麼？

---

## 十二、【待填】我怎麼決定一篇文章的難度節奏

> 💡 這裡填你在設計課程時的心法——什麼時候放慢、什麼時候加速、什麼時候留白讓學生自己想。
>
> 參考方向：
> - 你怎麼判斷「這裡要多說」vs「這裡直接帶過」？
> - 你會在哪種情況下故意不解釋，讓學生自己摸索？
> - 你怎麼決定「這個概念值得一個類比」vs「直接說就好」？

---

## 十三、【待填】我對「好的程式碼範例」的標準

> 💡 這裡填你在挑選或設計範例程式碼時的偏好與原則。
>
> 參考方向：
> - 你喜歡用真實資料（咖啡廳銷售、社團幹部名單）還是假資料（foo/bar）？為什麼？
> - 範例程式碼你習慣多長？一個完整功能，還是只示範一個概念？
> - 你怎麼決定要不要把「完整程式」跟「片段說明」都給？

---

## 十四、【待填】讓文章「有溫度」的細節習慣

> 💡 這裡填那些讓你的文章跟別人不一樣的小細節——不是大原則，是那種「你才會這樣寫」的習慣。
>
> 參考方向：
> - 你什麼時候會加 emoji？什麼時候不加？
> - 你怎麼在技術文章裡放「人味」？（murmur、括號吐槽、小故事...）
> - 你有沒有特別喜歡用的標點符號節奏，或特別避免的寫法？

## 十五、【待填】我認為「教會了」的標準是什麼

> 💡 這裡填你評估一篇教學是否成功的個人標準。
>
> 參考方向：
> - 學生做完 TodoList 就算學會，還是要能自己延伸？
> - 你怎麼設計「驗收點」讓學生自己確認有沒有懂？
> - 如果學生只記住一件事，你希望是哪件事？
